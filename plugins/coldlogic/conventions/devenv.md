# Dev environment

- Every tool runs through the project's devenv shell: `devenv shell --quiet -- <cmd>`. Never `nix develop`.
- System dependencies and environment setup go in `devenv.nix`, not in ad-hoc installs.
- `scripts/check.sh` is the gate. Never commit on a red gate, and never weaken a test to pass it: fix the code or flag the spec.
- Never pipe the gate through something that hides its exit status (`| tail`). Check the exit status directly.
- `.claude/settings.json` is generated by devenv and read-only. Change settings in Nix (`claude.code.*` or `files` in `devenv.nix`).
- Change project files only with `Edit` and `Write`, even where the harness suggests shell edits: never `sed -i`, `perl -i`, `tee`, or a `>`/`>>` redirect or heredoc script that writes into the project. Heredoc commit messages, `--body-file -`, and redirects to `$TMPDIR`, the scratchpad or `/dev/null` are fine.
- Never chain a file-content edit and a command in one Bash call (`sed -i … && scripts/check.sh`): `Edit` first, then run the command. Chained `git`, `mkdir` or `rm` are fine.

## When a command is blocked

- The sandbox, deny rules and coldlogic guard are deliberate. Never retry a blocked command unsandboxed, reworded, or another way that does the same thing.
- If it's legitimate and needed, propose the narrowest permission change in a PR: shared needs in `coldlogic-devenv` (`devenv.nix` or the language profile), a project's own in its `devenv.nix` (`claude.code.permissions.rules` or the settings `sandbox`). Say what was blocked and why. Open the ticket too (process.md).
- Allow rules name the command inside the devenv wrapper (`cargo test *`), not the wrapper.
- `.env` and its variants can't be read or written. For a new variable, add it to `.env.example` and put what the real file needs in an issue for the user (asking.md).
