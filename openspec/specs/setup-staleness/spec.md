# setup-staleness Specification

## Purpose
At the start of a new session, the coldlogic plugin reports any part of the shared Cold Logic setup that has fallen behind, with the command that fixes it, so the session can tell the user.

## Requirements

### Requirement: The staleness check runs at startup only
The plugin SHALL register `scripts/staleness.sh` as a SessionStart command hook with the `startup` matcher, so it runs when a session starts fresh and not when one is resumed, cleared or compacted. It SHALL check the project at `$CLAUDE_PROJECT_DIR`, or the working directory when that is unset.

Tested by: none.

#### Scenario: Fresh session
- **WHEN** a new session starts in a project with the plugin enabled
- **THEN** the staleness check runs against the project directory

#### Scenario: Resumed session
- **WHEN** a session is resumed
- **THEN** the staleness check doesn't run

### Requirement: Findings are reported as one instruction to the session
When any check finds something, the hook SHALL print one line telling the session that the shared Cold Logic setup is out of date and to mention it to the user once, at the start of its first reply, with the fix for each item, followed by one `- ` bullet per finding. When nothing is found it SHALL print nothing.

Tested by: none.

#### Scenario: Two findings
- **WHEN** the devenv pin is behind and the OpenSpec skills are stale
- **THEN** the output is the instruction line followed by two bullets, each ending with `run: <command>`

#### Scenario: Everything current
- **WHEN** no check finds anything
- **THEN** the hook prints nothing

### Requirement: A coldlogic-devenv pin that differs from its remote is reported
When the project's `devenv.lock` locks `coldlogic-devenv` from a `github` or `git` source, the hook SHALL compare the locked revision with the remote's `HEAD` from `git ls-remote` (3-second limit, no credential prompt). Any difference SHALL be reported as `behind`, with both short revisions and `run: devenv update coldlogic-devenv`, whichever way they differ. A local path input SHALL be skipped.

Tested by: none.

#### Scenario: Pin behind
- **WHEN** the lock pins `6dfb864…` and the remote's `HEAD` is `7026dff…`
- **THEN** the finding is `coldlogic-devenv is behind (locked 6dfb864, latest 7026dff); run: devenv update coldlogic-devenv`

#### Scenario: Pin ahead of the remote or on another branch
- **WHEN** the lock pins a revision that is ahead of the remote's `HEAD`, or on another branch
- **THEN** the finding still says `coldlogic-devenv is behind (locked <pin>, latest <head>)` and suggests `devenv update coldlogic-devenv`

#### Scenario: Remote unreachable
- **WHEN** `git ls-remote` fails or takes longer than 3 seconds
- **THEN** no finding is reported for the pin

#### Scenario: Module used from a local path
- **WHEN** the lock's `coldlogic-devenv` node has type `path`
- **THEN** the pin isn't checked

### Requirement: OpenSpec skills from another CLI version are reported
When `openspec` is on `PATH` and the project has `.claude/skills`, the hook SHALL join the sorted, distinct `generatedBy` values from `.claude/skills/openspec-*/SKILL.md` with commas and compare that string with the first line of `openspec --version`. Any difference SHALL be reported with `run: openspec update`, so skills of mixed versions always are. When either string is empty the check SHALL be skipped silently.

Tested by: none.

#### Scenario: Skills from an older CLI
- **WHEN** the skills say `generatedBy: "1.2.0"` and `openspec --version` prints `1.3.0`
- **THEN** the finding is `OpenSpec skills were generated by 1.2.0 but the CLI is 1.3.0; run: openspec update`

#### Scenario: Skills of mixed versions
- **WHEN** some skills say `generatedBy: "1.2.0"`, others `generatedBy: "1.3.0"`, and `openspec --version` prints `1.3.0`
- **THEN** the finding is `OpenSpec skills were generated by 1.2.0,1.3.0 but the CLI is 1.3.0; run: openspec update`

#### Scenario: Empty generatedBy
- **WHEN** every skill says `generatedBy: ""`
- **THEN** the check is skipped and nothing is reported

#### Scenario: CLI version unreadable
- **WHEN** `openspec --version` fails or prints nothing
- **THEN** the check is skipped and nothing is reported

#### Scenario: No OpenSpec skills
- **WHEN** no `openspec-*` skill has a `generatedBy` line
- **THEN** no OpenSpec finding is reported

### Requirement: Prunable auto-installed plugins are reported
When `claude` is on `PATH`, the hook SHALL run `claude plugin prune --dry-run` from the project directory at project scope and at user scope (5-second limit each). For each scope whose output is non-empty and doesn't start with `Nothing to prune`, it SHALL report `run: claude plugin prune --scope <scope>`.

Tested by: none.

#### Scenario: A dependency was removed
- **WHEN** a plugin dropped from `dependencies` is still installed at project scope
- **THEN** the finding is `Unneeded auto-installed plugins at project scope; run: claude plugin prune --scope project`

#### Scenario: Nothing to prune
- **WHEN** both dry runs print `Nothing to prune`
- **THEN** no prune finding is reported

### Requirement: The staleness check never fails the session
The hook SHALL exit 0 whatever its checks find or fail on. Each check SHALL skip itself when a tool it needs (`jq`, `git`, `openspec`, `claude`) or a file it reads is absent, and the time limits SHALL work without coreutils' `timeout`.

Tested by: none.

#### Scenario: No devenv.lock and no tools
- **WHEN** the project has no `devenv.lock` and neither `openspec` nor `claude` is on `PATH`
- **THEN** the hook prints nothing and exits 0

#### Scenario: Stock macOS
- **WHEN** `timeout` isn't on `PATH`
- **THEN** each network or CLI call is still stopped after its limit
